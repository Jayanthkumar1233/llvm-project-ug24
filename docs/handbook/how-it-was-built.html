01

The problem: a chip that nothing can program

A processor is a piece of silicon that reads numbers out of memory and does what each number tells it to do. The numbers are called machine code, and every family of processor uses a different set of them. The number that means "add these two registers" on an Intel chip means something else entirely on an ARM chip, and nothing at all on a chip neither company has ever heard of.

The uG24 is that third kind. It is a custom 8-bit microprocessor designed in-house. When this work started it existed as two documents — a specification PDF and a spreadsheet of instruction encodings — and as design files. What did not exist was any way to write a program for it in a language a person would want to use.

In plain terms

You cannot download a compiler for a chip that has just been invented, for the same reason you cannot download a Klingon–English dictionary for a language someone made up last week. Somebody has to write it. This handbook is the record of writing it.

Writing machine code by hand is possible and completely impractical: a page of C becomes hundreds of hand-placed numbers, and one mistyped digit is a bug nothing will catch. What everybody actually wants is to write c = a + b; and have a program work out which numbers that means. That program is a compiler, and a compiler for a processor that is not the one you are sitting at is a cross compiler.

So the job was: build a cross compiler for the uG24, plus everything a compiler needs around it to be useful — an assembler, a linker, a startup file, a C library, and something to run the results on, because no silicon exists yet either.

What "built" means here

None of this was written from a blank page. LLVM is an open-source compiler framework used by Apple, Google, Sony and most of the embedded industry, and it is deliberately built so that a new processor can be added to it. Everything that is not specific to a processor — parsing C, optimising, register allocation, the structure of the linker — already existed and was reused.

What had to be written is the part that knows about the uG24: about 11,300 lines across the compiler, the assembler, the linker, the runtime library, the simulator and the tests. That is the subject of this document.

02

What a compiler actually does

A compiler is not one program. It is a chain of them, each handing its output to the next. Knowing the chain is most of what you need to follow the rest of this handbook, because each phase of the work built one link in it.

The five links, one paragraph each

The front end reads your C, checks it makes sense, and reports your typos. It then throws the C away and emits intermediate representation — LLVM IR — a simplified, processor-independent form of the same program. IR is where all the optimisation happens, and it knows nothing about the uG24 beyond a short description of how wide its integers and pointers are.

The back end turns IR into instructions this particular processor has. This is the largest piece of the work and the subject of phases 3 to 6 below. It has to choose instructions, decide which of the sixteen registers holds which value, arrange the stack, and finally write out the exact bits.

The assembler is the same machinery seen from the other side: it turns human-written text like adi r0, 1 into the same bits. Both use one shared description of the instruction set, which is why they can never disagree.

The linker takes the object files — one per source file, each still full of blanks where an address should be — joins them with the startup code and the library, decides where everything lives in memory, and fills in the blanks. Its instructions come from a linker script, which is the map of the chip's memory.

The runtime is the code that runs before and beneath your program: the few dozen instructions between power-on and the first line of main, and the library functions (printf, malloc, memcpy) that C programs assume are simply there. On a desktop the operating system provides all of it. Here there is no operating system, so it was written too.

03

The machine we had to hit

Everything difficult about this project follows from four facts about the uG24.

FactWhat it means for a compiler
The ALU is 8 bits wide The arithmetic unit adds one byte at a time. But C's int on this target is 16 bits, so a single a + b in C is two machine instructions, and the second one has to pick up the carry the first produced.
Addresses are 16 bits 64 KB of memory total, for code and data together. A pointer does not fit in a register; it takes a pair of them. Program size matters constantly.
There are 16 registers R0–R15, one byte each, which also pair up into eight 16-bit registers. Two of the sixteen had to be reserved for the compiler's own use, leaving fourteen for your program.
Instructions are 16 bits, fixed Every instruction is exactly two bytes (except two jumps, which take a second fetch). That is a tight budget: an instruction that names two registers and an 8-bit constant has already spent all sixteen bits.
In plain terms

Think of the processor as a clerk who can only add two-digit numbers and has sixteen scraps of paper to work on. Asking for a four-digit sum is fine, but the clerk has to do it in two steps and remember to carry. The compiler's job is to break every calculation in your program down into steps that small, and to keep track of which scrap holds what.

Why a 16-bit add takes two instructions

This one picture explains most of the back end's existence.

P1

Reading the hardware documents

Before a line of code, the two source documents had to be turned into something exact enough to build on. A compiler cannot cope with "roughly": if the shift instruction encodes its amount minus one and you assume it encodes the amount, every shift in every program is off by one and nothing tells you.

Two things came out of this phase, and both shaped everything after.

The spreadsheet is the ground truth

The PDF and the encoding spreadsheet disagreed in places. The spreadsheet won, every time, because it is the document generated from the design rather than written about it. Where they conflicted, the conflict was recorded rather than quietly resolved.

Fifty-one questions the documents could not answer

Some things a compiler must know simply are not written down anywhere: whether the 8-bit immediates are signed, whether the pipeline stalls automatically when one instruction needs the result of the one before, what the board will strap the reset stack pointer to. Each of these became a numbered query to the silicon team.

Where a query blocked progress, the toolchain made a decision, implemented it, and wrote down both the decision and the fact that it was a decision. That record is docs/uG24-assumptions.md, and it is the reason a wrong guess is recoverable: each assumption names the one file that changes if the answer differs.

The discipline that matters

An assumption you have written down is a task. An assumption you have forgotten making is a bug that will surface on silicon, months later, looking like something else entirely. Every choice this toolchain made in the absence of an answer is in that file, with the reasoning and the fix.

P2

Teaching the tools that the chip exists

The first code written did almost nothing, and was the right place to start: it gave the project a milestone it could actually reach.

Every processor LLVM knows is identified by a triple, a short string naming the architecture, the vendor, the operating system and the ABI. The uG24's is ug24-unknown-none-eabi — a uG24, from no particular vendor, with no operating system. Separately, executable files carry a number saying which machine they are for; ARM is 40, x86-64 is 62, and the uG24 was assigned 0x9240 in the private range.

The first thing that worked
$ clang --print-targets | grep ug24
    ug24       - uG24 8-bit Microprocessor

At this point the compiler could not produce a single instruction. But it knew the target existed, it would accept --target=ug24-unknown-none-eabi, and the build was wired end to end. Everything after this was filling in a shape that already fit.

Telling the front end how wide things are

One small piece of this phase has an outsized effect later. The front end needs to know, for this target, how big an int is, how big a pointer is, and what each type's alignment is — written as a terse data layout string:

clang/lib/Basic/Targets/UG24.h
e-m:e-p:16:8-i8:8-i16:8-i32:8-i64:8-f32:8-f64:8-a:8-n8:16-S8

p:16:8 says pointers are 16 bits wide and aligned to 8 bits — one byte. Getting that second number wrong produced one of the hardest bugs in the whole project, described in phase 11.

P3

Machine code: describing 51 instructions once

The next phase deliberately skipped over compiling C and went straight to the bottom of the stack: the exact bits.

Four separate tools need to agree about every instruction. The assembler turns adi r0, 1 into bits. The disassembler turns bits back into adi r0, 1. The compiler emits the same bits from its own internal form. The simulator reads them and does the arithmetic. If any one of the four disagrees with the others, you get a bug that looks like the wrong thing.

LLVM's answer is TableGen: a small declarative language in which you describe each instruction once — its name, its operands, its bit layout, how it prints — and from which the assembler, disassembler, encoder and matcher are all generated. Disagreement becomes structurally impossible.

llvm/lib/Target/UG24/UG24InstrInfo.td — one instruction, described once
def ADI : FI_RI<0b110, (outs GPR:$rd), (ins GPR:$rs, imm8:$imm),
                 "adi\t$rd, $imm", [...]>;

The uG24's instruction set has six encoding formats, chosen by the low bits of the instruction word — a compact scheme that squeezes a useful instruction set into two bytes each. All 51 encodings were transcribed from the spreadsheet and each was given two tests: one checking that the assembler produces the documented bits, and one checking that the disassembler turns those bits back into the same instruction.

Why start here

Encodings are the one part of the project where an outside authority says what "correct" means. Everything above this — which instruction to choose, where to put a variable — is a judgement call. Nailing down the layer that has a right answer first means that when something later goes wrong, you already know it is not the bits.

P4

The register file, and the two we gave away

Registers are the handful of storage slots inside the processor that instructions can name directly. The uG24 has sixteen of one byte each, and the same silicon is also addressable as eight 16-bit pairs. The compiler has to model that overlap precisely: writing to R8 changes the pair W, and the register allocator must never believe otherwise.

PairBytesRole
P0, P1R0–R3Arguments and scratch; also where a 64-bit return spills to
P2, P3R4–R7Preserved across calls. P3 doubles as the frame pointer when a function needs one
WR8, R9The 16-bit return value; also where MUL and DIV put their results
P5R10, R11R10 preserved; R11 reserved
DPTR1R12, R13Second 16-bit argument; second data pointer
DPTR0R14, R15Reserved — the memory base register

Why two registers had to be given up

DPTR0 is reserved because of how the uG24 reaches memory. Load and store do not take an address in the instruction; they take a displacement, and read the base address from DPTR0. If DPTR0 were available to the register allocator, every memory access would first have to shuffle a pointer into it and possibly save whatever was there. Dedicating the pair costs two registers and saves two instructions on every load and store in every program.

R11 is reserved as a scratch byte. The instructions that add with carry take a register, not a constant, so 16-bit arithmetic against a literal needs somewhere to put the literal's high byte — often at a point, after register allocation, where there is provably nothing free. One byte held permanently in reserve removes a whole class of impossible situations.

P5

Instruction selection: fitting C onto an 8-bit ALU

This is the heart of a back end. The input is LLVM IR — a program expressed in operations like "add these two 16-bit values" that no processor necessarily has. The output is uG24 instructions.

LLVM's mechanism is pattern matching over a graph. Each IR operation becomes a node; the back end supplies patterns saying "this shape of node becomes this instruction"; a generated matcher finds the best covering. Where a pattern exists, the work is one line of TableGen. The interesting part is everything that has no pattern.

Three kinds of problem, three answers

Operations the ALU cannot do in one go

A 16-bit add has no single instruction. The answer is a pseudo instruction: the matcher selects a placeholder called ADD16 that pretends to be one operation, the register allocator assigns a real pair to it, and only afterwards does a dedicated pass (UG24ExpandPseudo) split it into ADD on the low bytes and ADC on the high ones. Doing the split late means the allocator sees one operation on one pair, rather than two operations on four separate bytes it might scatter.

Operations the processor does not have at all

There is no 16-bit multiply, no division except 8-bit unsigned, no floating point and no variable shift. For these the back end emits a call to a helper function — a "libcall" — and the helper is written in C in the runtime library. a * b on two 16-bit values becomes lja __mulhi3, and __mulhi3 is a shift-and-add loop.

Operations whose result goes somewhere unusual

The hardware MUL writes its 16-bit product to W implicitly — W is not one of its operands. Comparisons set flags rather than producing a value. Both are handled by selecting a pseudo with a normal-looking destination and rewriting it after register allocation, so the ordinary machinery never has to understand the irregularity.

A trap worth knowing about

One optimisation in this area had to be deliberately removed. LLVM has a rewrite that hoists a logic operation out of two identical operands, and the back end had a rewrite that narrowed 16-bit logic to 8-bit. Together they formed a loop: each undid the other, and the compiler ran until it was killed. The fix is three lines and a long comment explaining why, so that nobody re-adds it — which had already happened once.

P6

Frames, calls, and an ABI nobody had written

When one function calls another, both sides need to agree on where the arguments are, where the result comes back, and which registers the callee is allowed to destroy. That agreement is the calling convention, and it is part of a larger agreement called the ABI.

On ARM or x86 the ABI is a published standard everybody implements. For the uG24 no such document exists. So one was invented, written down, and implemented in two places that must never drift apart: the front end, which decides what goes by value and what goes by reference, and the back end, which assigns the registers.

WhatWhere it goes
8-bit argumentsR0, R1, R2, R3, then the stack
16-bit arguments and pointersW, DPTR1, then the stack
Variadic calls (printf)Everything on the stack, fixed arguments included
Return, up to 32 bitsW, then DPTR1
Return, 64 bitsW, DPTR1, P0, P1
Anything larger, and every structThrough a hidden pointer the caller passes
Preserved across a callR4, R5, R6, R7, R10

The return address problem

The uG24 has one link register, RA, and no hardware stack for it. A call overwrites it. So a function that itself makes a call must push RA on entry and pop it before returning, while a function that makes none can skip both — worth doing, since it is two instructions on every leaf function in the program.

Why variadic functions put everything on the stack

printf("%d %d\n", a, b) is a problem: the callee has no idea how many arguments there are or what type they were. It walks them in memory. If the first few had been passed in registers, the callee would start reading from the wrong place. Passing everything on the stack for a variadic call — including the format string — is the one arrangement where both sides agree, and it is why the convention has a special case for it.

The frame pointer, added late

Most functions address their local variables as offsets from the stack pointer, which costs no register. A function containing a variable-length array cannot: it moves the stack pointer after the prologue, and every offset computed before that becomes wrong. Those functions — and only those — take P3 as a frame pointer, set once and left alone.

This was missing for most of the project, and the bug it caused is in phase 11.

P7

Linking: filling in the blanks

When the compiler processes one file it does not know where anything will end up in memory. A call to a function in another file is emitted with a hole where the address goes, plus a note saying "put the address of printf here, as a 16-bit value". That note is a relocation, and filling it in is the linker's job.

The uG24 needed seven relocation types. Two are unusual enough to be worth explaining: because an instruction is only 16 bits and a full address is 16 bits too, an address cannot be embedded in one instruction. It is loaded a byte at a time, with the relocation selecting which byte:

Loading a 16-bit address into a register pair
mvi  r14, lo8(message)   ; low byte  → R_UG24_LO8
mvi  r15, hi8(message)   ; high byte → R_UG24_HI8

The memory map

The linker also needs to be told what the 64 KB actually looks like. That description is the linker script, and it encodes several decisions at once.

P8

The runtime: what happens before main

On a desktop, a great deal happens between typing the program's name and your first line running. Here, nothing does — unless you write it. The startup file crt0.s is what the processor executes out of reset, and it has four jobs before it can call main:

  1. Set the stack pointer. Until this happens there is nowhere to put a return address, so no function call is possible.
  2. Select the data pointer. One flag bit chooses which of the two pointer registers load and store use. The compiler assumes DPTR0; crt0 makes that true once, for the whole program.
  3. Zero .bss. C promises that a global without an initialiser starts at zero. Nothing zeroes memory for you, so a loop does it.
  4. Copy .data. A global that starts at 5 has that 5 stored somewhere in the program image; it has to be copied to where the variable lives.

Only then does it call main. When main returns there is nothing to return to, so it halts.

A detail that looks like waste

In the current memory map, .data's stored copy and its run-time home are the same address, so the copy loop finds them equal and exits immediately. It is there anyway: the moment the chip is configured with separate program and data memories — which the specification says is a per-SoC option — that loop starts doing real work, with no change to the startup code. Writing it now costs a dozen instructions and removes a future silent failure.

The library beneath the library

Alongside crt0 sits libug24.a, which holds every function the back end can emit a call to. Some of it is what any C programmer expects — memcpy, strlen. The rest is arithmetic the processor cannot do: __mulhi3, __udivsi3, __muldi3, __addsf3. A C programmer never names these; the compiler emits the calls.

Why the runtime is built with -ffreestanding -fno-builtin

Without those flags the optimiser recognises the shift loop inside __ashlhi3 as "a shift", and rewrites it as a call to __ashlhi3. The function calls itself forever. The flags tell the compiler it may not assume the standard library exists — which, while you are building it, it does not.

P9

The simulator, and why it mattered most

At this point the toolchain produced executables. Whether those executables did the right thing was unknown, because there was no uG24 to run them on.

So one was written: ug24sim, 810 lines of C that load an ELF file into a 64 KB array and interpret instructions until the program halts. It is not a model of the silicon — it is a model of the specification, which is a meaningfully weaker thing and is discussed under what this cannot tell us.

Compile and run, on a machine with no uG24 in it
$ clang --target=ug24-unknown-none-eabi -Os hello.c -o hello.elf
$ ug24sim hello.elf --quiet
Hello ug24

This changed the character of the project completely. Before the simulator, a bug looked like assembly that seemed plausible. After it, a bug looked like a program printing 5 4 instead of 5 5 — which is something you can bisect, minimise and fix. Every wrong-code bug found in this project was found because something could execute.

The two features that earn their keep

A UART and an exit register. Three addresses in the top page: write a byte to 0xFF00 and it appears on the terminal; write to 0xFF02 and the simulator exits with that status. That is enough for printf to work and for a test to report pass or fail.

A stack-window check. The simulator reads the heap and stack boundaries out of the program's own symbol table and checks the stack pointer after every single instruction. On real hardware, a stack that grows into the heap corrupts data and the program carries on producing wrong answers. Here it stops immediately with a message naming the addresses. That check is how the variable-length-array bug was caught the moment it happened rather than three functions later.

P10

A C library for a machine with no operating system

A compiler that cannot compile printf("hello\n") is not much use to the person who has to write firmware with it. The standard library on a normal system is mostly a thin layer over the operating system; with no operating system, all of it has to be real code.

HeaderWhat was written
<stdio.h>The whole printf family — every conversion and flag, including %f, %e and %g — writing to the UART or to a buffer. No scanf: there is no input device.
<stdlib.h>malloc, free, realloc over the heap the linker script marks out; the string conversions; qsort; abs and div.
<string.h>The mem* and str* functions, which the compiler also emits calls to on its own.
<setjmp.h>Written in assembly, because a C function cannot see the return address the call left in a register, nor the stack pointer its own prologue has already moved.
<ug24.h>Not standard: the peripheral registers and the interrupt controller, for code that talks to hardware directly.

Arithmetic the processor does not have

Underneath the library sits a second one nobody calls by name. A 64-bit multiply becomes __muldi3; a floating-point addition becomes __addsf3. These were written to work in terms of 16-bit limbs, because that is what the machine has, and carefully enough that they never accidentally call themselves.

A decision worth knowing about

On this target double is 32-bit IEEE single precision, not 64-bit — the same choice AVR makes. It halves the size of the floating-point library and doubles its speed, at the cost of precision that an 8-bit microcontroller was never going to use well. Code that genuinely needs 53 bits of mantissa will not get it here.

The cost of a feature, measured

printf("Hello ug24\n") produces a 300-byte program. The same program with a %f and a float to put through it is about 25 KB, because %f pulls in the soft-float library, and the decimal conversion pulls in 64-bit division behind it. On a 64 KB part that is a third of the address space.

So the float formatter is linked on demand. It is declared in printf's source but not defined there, marked weak; an undefined weak symbol does not make the linker pull anything out of the library. A program that does any floating-point arithmetic has already pulled the float runtime in, and the formatter resolves. A program that does none never pays for it.

Making a program smaller by 98%

One change in the driver is responsible for most of the size of every program here. By default the linker's unit of work is the whole object file: one call to printf drags in the entire formatter and all the arithmetic behind it whether or not you used any of it. Compiling each function into its own section and letting the linker discard unreferenced sections changes the unit to the function.

P11

Finding the bugs: three layers, three real failures

A compiler is a program whose bugs are other people's mysteries. If it produces subtly wrong code, the person debugging it is looking at their source, which is correct. So the testing here is deliberately layered, and each layer catches a class of bug the layer below it structurally cannot see.

Bug one: %s printed one byte late

Strings came out as garbage, and the amount of garbage depended on how many local variables the calling function had. That last part is the clue: the bug was not in printf, it was in where the arguments had been put.

The data-layout string said pointers were aligned to two bytes; the front end said one. When printf walked its variadic arguments it rounded the list pointer up to an even address, and the caller had not. Whenever the preceding argument happened to end on an odd address, every argument after it was read one byte late. Changing p:16:16 to p:16:8 fixed it — a four-character edit for a bug that had looked like a broken library.

Bug two: a variable-length array returned into the stack

A function with both a normal local and a char buf[n] printed the right answers and then jumped somewhere meaningless. The simulator's stack check caught it on the instruction it happened.

The cause was the missing frame pointer. Allocating the array moved the stack pointer; the epilogue restored it by adding back only what the prologue had subtracted; the difference was still there when RA was popped, so the function returned to whatever happened to be at that address. The fix is described in phase 6: a function like this takes P3 as a frame pointer, and the epilogue restores the stack pointer from it.

Bug three: a >> 32 gave the wrong half, only without optimisation

This one is the reason the third layer runs at five optimisation levels. Taking the top half of a 64-bit local returned the bottom half — at -O0. At every other level it was correct, which is the opposite of the usual pattern and made it look like a fluke.

The chain took a while to unpick. LLVM's frame code has a flag saying whether the target can realign the stack; it defaults to yes, and nothing here had said otherwise. Because it was yes, the frame bookkeeping kept the alignment an unsigned long long would prefer — eight bytes — rather than the one byte this stack can actually promise. A later analysis asked "what do I know about the low bits of this slot's address?", was told they were zero, and passed that on. Then a routine that computes base + 6 saw it could use a bitwise OR instead of an add, because OR is identical when the bits do not overlap.

On a byte-granular stack they do overlap. base | 6 landed on the wrong slot and read back a different limb of the same variable. One line — declaring the stack not realignable — removed the whole chain.

What this says about the method

Nothing short of running a real program, at a level nobody normally ships, would have found this. It was not in the code that was changed; it had been latent since the data layout was written, and surfaced only when 64-bit arithmetic was added and gave it something to be wrong about.

P12

Making it configurable, and adding interrupts

Parts that do not all have the same hardware

The specification says the multiplier and the divider are optional blocks: a customer's system-on-chip may leave either out. A compiler that emits mul unconditionally produces code that such a part cannot execute.

So both became subtarget features. They default to present, since that is what the documents describe; -mcpu=ug24-base compiles for a part with neither, and the same operations quietly become calls to the runtime helpers — which are shift-and-add loops and need no hardware of their own, so the library does not have to be rebuilt to match. The assembler rejects mul in that configuration too, rather than encoding something the part cannot run.

Interrupts, and a model built on a guess

An interrupt is the hardware stopping your program mid-instruction to run a handler, then resuming as if nothing happened. For a microcontroller it is the central feature — it is how a chip responds to a timer, a button, an arriving byte.

Making a handler work is mostly a compiler problem. An ordinary function is allowed to destroy half the registers, because its caller knew that and saved what it needed. A handler has no caller: it interrupted code that was in the middle of something and expects every register back. So __attribute__((interrupt)) makes the compiler preserve everything the handler writes — including the two reserved registers, which the ordinary machinery cannot even see — and return by the interrupt's own route rather than through RA.

This part rests on assumptions

The specification names the interrupt enable bits and nothing else. Where the vector table lives, what the hardware pushes when it takes an interrupt, how a source is acknowledged — none of it is written down. A coherent model was implemented using only instructions and flag bits the specification does define, and every assumption in it is listed in docs/uG24-assumptions.md.

This is the most dangerous item in the project, precisely because it works. Handlers compile, run and pass their tests under the assumed model; if the model is wrong they will fail on silicon and the symptom will not point here.

What this testing cannot tell us

Every result above was produced by a simulator written from the same documents as the compiler. If both misread the same sentence, both agree and the tests pass. That is not a hypothetical concern — three open questions would silently invalidate generated code if the answers differ from what was assumed:

QueryQuestionWhat breaks if the answer differs
I2Is there a load-use delay?The compiler emits a load followed immediately by a use of the loaded register constantly. If the hardware needs a gap, essentially every function is wrong.
I1Is the pipeline fully interlocked?No fences are inserted anywhere. Failures would look like intermittent, data-dependent flakiness rather than compiler bugs.
I3Which PC does MOV Xd, PC read?The indirect call computes its return address from it. If the answer differs, every call through a function pointer returns into the middle of an instruction.

The single most valuable thing the hardware team could provide is not an answer to any one of these. It is an executable model of the core — then the simulator stops being an assumption and starts being something checkable, and all fifty-one queries can be settled by experiment.

Glossary

Terms used above, in the sense they are used here.

ABI
Application Binary Interface. The agreement about how compiled code fits together: where arguments go, how big types are, what a function may destroy. Two compilers that disagree produce code that cannot be linked safely.
Assembler
Turns human-readable instruction text into machine code. The inverse of a disassembler.
Back end
The processor-specific half of a compiler: chooses instructions, allocates registers, lays out stack frames, writes the bits.
Calling convention
The part of the ABI that says where arguments and return values live, and which registers survive a call.
Cross compiler
A compiler that runs on one kind of machine and produces code for another. Everything here runs on an x86-64 PC and produces uG24 code.
ELF
The file format for compiled objects and executables on Linux and on most embedded targets. Carries code, data, symbol names and relocations.
Front end
The language-specific half: reads C, reports errors, produces IR. Knows almost nothing about the target processor.
IR
Intermediate Representation. A simplified, processor-independent form of the program, and where optimisation happens.
Libcall
A call the compiler inserts on your behalf to a helper function, for an operation the processor cannot do — a 64-bit multiply, a floating-point add.
Linker
Joins compiled pieces into one executable and fills in every address that was unknown when each piece was compiled.
Linker script
The file that tells the linker what the memory looks like and where each kind of content goes.
MMIO
Memory-mapped I/O. Addresses that are not memory but device registers: writing to 0xFF00 sends a byte to the serial port.
Prologue / epilogue
The instructions a function runs on entry and exit to set up and tear down its stack frame.
Pseudo instruction
A placeholder the compiler uses internally that looks like one instruction and is replaced by several real ones later, after register allocation.
Register allocation
Deciding which of the processor's few registers holds which of the program's many values at each point, and spilling the rest to memory.
Relocation
A note in an object file saying "an address goes here, and this is which address and in what form". The linker acts on them.
Simulator (ISS)
A program that pretends to be the processor, executing its instructions one at a time. Here it is ug24sim, and it is the only thing that has ever run uG24 code.
Soft float
Floating-point arithmetic done by library functions because the processor has no floating-point hardware.
Subtarget feature
An optional piece of hardware that some members of a processor family have and others do not — here, the multiplier and the divider.
TableGen
LLVM's declarative language for describing a processor once and generating the assembler, disassembler, encoder and pattern matcher from that one description.
Triple
The string identifying a target: ug24-unknown-none-eabi is a uG24, no vendor, no operating system.
