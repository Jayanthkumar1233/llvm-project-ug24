Why the GCC cross packages

They are not used to compile your code. They supply the sysroots — target headers and libc — and the libgcc and crtbegin objects that clang links against for hosted targets. swig and libedit-dev are required by LLDB. qemu-system-arm is needed to execute bare-metal images.

2.4 Environment variables

Add these to ~/.bashrc so they survive new shells.

~/.bashrc
export LLVM_WORK=$HOME/llvm-arm-cross
export SYSROOT_ARMHF=/usr/arm-linux-gnueabihf
export SYSROOT_ARM64=/usr/aarch64-linux-gnu
export SYSROOT_NONE=$LLVM_WORK/sysroot-none-eabi

export PATH=$LLVM_WORK/stage1/bin:$PATH
shell
source ~/.bashrc && echo "$LLVM_WORK | $SYSROOT_ARMHF"
expected 
/home/<user>/llvm-arm-cross | /usr/arm-linux-gnueabihf
An unset variable fails silently

--sysroot=$SYSROOT_ARMHF with the variable unset expands to --sysroot=, which clang accepts and ignores. The result is a confusing stdio.h not found much later. Always confirm the echo above before building.

Prepare the sysroots

A sysroot is a directory tree holding the target's headers and libraries. Clang uses --sysroot to find them without touching host paths.

4.1 Sysroot options

MethodBest forHow
Option A — installed GCC sysrootQuick start, already on the host/usr/arm-linux-gnueabihf
Option B — debootstrapA clean minimal Debian rootfssudo debootstrap --arch armhf ...
Option C — newlib copyBare metal, no OScp /usr/lib/arm-none-eabi/...

4.2 Option A — use the installed GCC sysroot (recommended)

shell
# 32-bit ARM hard-float
export SYSROOT_ARMHF=/usr/arm-linux-gnueabihf

# 64-bit ARM
export SYSROOT_ARM64=/usr/aarch64-linux-gnu

# Verify headers and libraries are present
ls $SYSROOT_ARMHF/include/ | head -6
ls $SYSROOT_ARMHF/lib/ | grep -E '^lib(c|m)\.'
expected 
aio.h  aliases.h  alloca.h  a.out.h  argp.h  argz.h
libc.a
libc.so
libc.so.6
libm.a

4.3 Option B — build a clean sysroot with debootstrap

shell
export SYSROOT_ARMHF=$LLVM_WORK/sysroot-armhf
mkdir -p $SYSROOT_ARMHF

sudo debootstrap --arch=armhf \
    --include=libstdc++-12-dev,libc6-dev,libgcc-12-dev \
    bullseye $SYSROOT_ARMHF http://deb.debian.org/debian

# Fix absolute symlinks, which break when read from the host
cd $SYSROOT_ARMHF
find . -type l | while read link; do
    target=$(readlink "$link")
    [ "${target#/}" != "$target" ] && ln -sf "${SYSROOT_ARMHF}${target}" "$link"
done

# MUST verify - a partial debootstrap looks like success
ls $SYSROOT_ARMHF/usr/include/stdio.h
find $SYSROOT_ARMHF -name 'libc.so*' | head -2
Option B failed on the previous build — verify it

The debootstrap in the earlier build died after downloading the package index, leaving a directory with five files and no libc. debootstrap exits without an obvious error, and the failure only surfaces later as unresolvable link errors. If the two checks above do not both succeed, delete the directory and use Option A.

Stage 1 — native host clang

Stage 1 is an x86_64 clang with the ARM and AArch64 back ends enabled. It is used to build every later stage: clang building clang produces a better result than the system GCC, and guarantees all stages use one front end. 40–90 min on 8 cores

5.1Create the build directory
shell
cd $LLVM_WORK/llvm-project
mkdir -p build-stage1 && cd build-stage1
5.2Configure with CMake
shell
cmake -G Ninja ../llvm \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_INSTALL_PREFIX=$LLVM_WORK/stage1 \
    -DLLVM_TARGETS_TO_BUILD="X86;ARM;AArch64" \
    -DLLVM_ENABLE_PROJECTS="clang;lld" \
    -DLLVM_ENABLE_RUNTIMES="" \
    -DLLVM_BUILD_TOOLS=ON \
    -DLLVM_INCLUDE_TESTS=OFF \
    -DLLVM_INCLUDE_EXAMPLES=OFF \
    -DCLANG_DEFAULT_LINKER=lld \
    -DLLVM_PARALLEL_LINK_JOBS=1
FlagPurpose
LLVM_TARGETS_TO_BUILDHost (X86) plus both ARM back ends
LLVM_ENABLE_PROJECTSClang and LLD. LLDB is added in Stage 2 only
LLVM_ENABLE_RUNTIMES=""No compiler-rt or libcxx here — Stage 1 is a build tool, not a shipped toolchain
LLVM_BUILD_TOOLS=ONBuilds llvm-config, llvm-ar, llvm-nm etc., needed by later stages
CMAKE_BUILD_TYPE=ReleaseNever use Debug: 3× larger, far slower
LLVM_PARALLEL_LINK_JOBS=1Each link job needs several GB. Parallel links get OOM-killed on 16 GB
5.3Build and install

Each target gets its own independent build directory. All three use the Stage 1 clang as the compiler.

6.1 Target A — armv7-linux-gnueabihf

6.3 Target C — arm-none-eabi (Cortex-M bare metal)

No OS, no dynamic linking.60–120 min

compiler-rt must not go in LLVM_ENABLE_RUNTIMES here

If compiler-rt is listed in LLVM_ENABLE_RUNTIMES for this build, the runtimes sub-build auto-selects -mfloat-abi=soft, which disables the VFP registers. The VFP assembly builtins (fixunssfsivfp.S and friends) then fail with instruction requires: VFP2.

The COMPILER_RT_* flags below are cache variables. They are harmless here — nothing reads them while compiler-rt is not being configured — and are kept so the same cache serves §7.2. The builtins are actually built in §7.2, where the correct -mfpu and -mfloat-abi flags are given explicitly.

6.3.1Configure, build and install
shell
cd $LLVM_WORK/llvm-project
mkdir -p build-none-eabi && cd build-none-eabi

cmake -G Ninja ../llvm \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_INSTALL_PREFIX=$LLVM_WORK/toolchain-none-eabi \
    -DCMAKE_C_COMPILER=$LLVM_WORK/stage1/bin/clang \
    -DCMAKE_CXX_COMPILER=$LLVM_WORK/stage1/bin/clang++ \
    -DLLVM_TARGETS_TO_BUILD="ARM" \
    -DLLVM_ENABLE_PROJECTS="clang;lld" \
    -DLLVM_ENABLE_RUNTIMES="" \
    -DLLVM_DEFAULT_TARGET_TRIPLE="arm-none-eabi" \
    -DLLVM_HOST_TRIPLE="x86_64-linux-gnu" \
    -DCLANG_DEFAULT_LINKER=lld \
    -DCOMPILER_RT_BAREMETAL_BUILD=ON \
    -DCOMPILER_RT_BUILD_BUILTINS=ON \
    -DCOMPILER_RT_BUILD_SANITIZERS=OFF \
    -DCOMPILER_RT_BUILD_XRAY=OFF \
    -DCOMPILER_RT_BUILD_LIBFUZZER=OFF \
    -DCOMPILER_RT_BUILD_PROFILE=OFF \
    -DLLVM_PARALLEL_LINK_JOBS=1 \

compiler-rt builtins

compiler-rt supplies the low-level routines clang emits calls to — 64-bit division, soft-float, stack protection — replacing libgcc. It must be cross-compiled once per target architecture.

7.1 compiler-rt for armv7-linux-gnueabihf

shell
cd $LLVM_WORK/llvm-project
mkdir -p build-rt-armhf && cd build-rt-armhf

# Pick up whichever cross-GCC version is installed
export GCC_ARM_VER=$(ls /usr/lib/gcc-cross/arm-linux-gnueabihf/ | tail -1)
echo "using cross GCC $GCC_ARM_VER"

cmake -G Ninja ../compiler-rt \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_INSTALL_PREFIX=$LLVM_WORK/toolchain-armhf \
    -DLLVM_CMAKE_DIR=$LLVM_WORK/stage1/lib/cmake/llvm \
    -DCMAKE_C_COMPILER=$LLVM_WORK/stage1/bin/clang \
    -DCMAKE_CXX_COMPILER=$LLVM_WORK/stage1/bin/clang++ \
    -DCMAKE_ASM_COMPILER=$LLVM_WORK/stage1/bin/clang \
    -DCMAKE_C_COMPILER_TARGET="armv7-linux-gnueabihf" \
    -DCMAKE_CXX_COMPILER_TARGET="armv7-linux-gnueabihf" \
    -DCMAKE_ASM_COMPILER_TARGET="armv7-linux-gnueabihf" \
    -DCMAKE_C_COMPILER_EXTERNAL_TOOLCHAIN=/usr \
    -DCMAKE_CXX_COMPILER_EXTERNAL_TOOLCHAIN=/usr \
    -DCMAKE_SYSROOT=/ \
    -DCMAKE_C_FLAGS="--gcc-toolchain=/usr -march=armv7-a -mfloat-abi=hard" \
    -DCMAKE_CXX_FLAGS="--gcc-toolchain=/usr -march=armv7-a -mfloat-abi=hard" \
    -DCMAKE_ASM_FLAGS="--gcc-toolchain=/usr -march=armv7-a -mfloat-abi=hard" \

7.2 compiler-rt builtins for arm-none-eabi (Cortex-M4) — optional

Set this aside on a first build

This step is not required to have a working bare-metal toolchain. Section 10.2 compiles with clang and links with arm-none-eabi-gcc, which brings its own libgcc — that path works whether or not §7.2 has been done.

Do §7.2 only when you want to link bare-metal images with ld.lld and no GNU tools at all, which §10.2.1 demonstrates. Skip it on a first pass and come back to it.

This section is corrected — Rev 1.1 did not work

The v1.1 recipe pointed CMake at ../compiler-rt without forcing the target, so COMPILER_RT_DEFAULT_TARGET_TRIPLE stayed at x86_64-unknown-linux-gnu. The build silently produced armhf libraries in build-rt-m4 and nothing bare-metal was ever installed. Linking then failed with undefined symbol: __aeabi_ldivmod.

Two changes fix it: point CMake at compiler-rt/lib/builtins rather than all of compiler-rt, and set COMPILER_RT_DEFAULT_TARGET_ONLY=ON so the triple is taken from CMAKE_C_COMPILER_TARGET. Do not also set COMPILER_RT_DEFAULT_TARGET_TRIPLE — the two conflict and configuration fails.

shell
cd $LLVM_WORK/llvm-project
mkdir -p build-rt-m4 && cd build-rt-m4

cmake -G Ninja ../compiler-rt/lib/builtins \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_INSTALL_PREFIX=$LLVM_WORK/toolchain-none-eabi/lib/clang/17 \
    -DCMAKE_C_COMPILER=$LLVM_WORK/stage1/bin/clang \
    -DCMAKE_ASM_COMPILER=$LLVM_WORK/stage1/bin/clang \
    -DCMAKE_C_COMPILER_TARGET=armv7em-none-eabi \
    -DCMAKE_ASM_COMPILER_TARGET=armv7em-none-eabi \
    -DCMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY \
    -DCMAKE_C_FLAGS="-mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard" \
    -DCMAKE_ASM_FLAGS="-mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard" \
    -DCOMPILER_RT_DEFAULT_TARGET_ONLY=ON \
    -DCOMPILER_RT_BAREMETAL_BUILD=ON \
    -DCOMPILER_RT_OS_DIR=baremetal \
    -DCOMPILER_RT_BUILD_BUILTINS=ON \

The uG24 target

uG24 is a custom 8-bit processor, not an upstream LLVM back end. The repository already contains the code generator, assembler, disassembler, ELF writer, lld back end, clang target and clang driver. 60–120 min

8.1Configure and build
shell
cd $LLVM_WORK/llvm-project

cmake -G Ninja -S llvm -B $LLVM_WORK/build-ug24 \
    -DCMAKE_BUILD_TYPE=Release \
    -DLLVM_TARGETS_TO_BUILD="UG24;AArch64;ARM" \
    -DLLVM_ENABLE_PROJECTS="clang;lld" \
    -DLLVM_ENABLE_RUNTIMES="" \
    -DCMAKE_C_COMPILER=$LLVM_WORK/stage1/bin/clang \
    -DCMAKE_CXX_COMPILER=$LLVM_WORK/stage1/bin/clang++ \
    -DLLVM_PARALLEL_LINK_JOBS=1

cd $LLVM_WORK
ninja -C build-ug24 -j$(nproc) \
    clang lld llc llvm-mc llvm-objdump llvm-readobj llvm-nm llvm-ar \
    FileCheck count not
Do not ask ninja for llvm-lit

Do not add llvm-lit to that ninja line. It is not a build target in any LLVM 17 tree — llvm/utils/llvm-lit/CMakeLists.txt only calls configure_file(), so cmake writes build-ug24/bin/llvm-lit at configure time and ninja never sees it. Asking for it gives ninja: error: unknown target 'llvm-lit', did you mean 'llvm-lib'? and stops the build before anything is compiled. The script is already on disk once the cmake above has finished.

FileCheck, count and not replace it: those are ninja targets, and llvm-lit needs all three to run the test suites in step 8.5.

ARM and AArch64 are included so this one build can also run the upstream regression suites, confirming that the shared-file changes (ELF.h, Triple.cpp, lld) broke nothing. This build is used in place, not installed.

8.3Build the runtime, simulator and tests

The uG24 compiler on its own cannot link a program: it needs a startup file, a support library, a linker script and a header, none of which exist until they are built with that compiler. ug24-setup.sh from the support bundle does that bootstrapping. It is reproduced in full here so it can be run by hand or recreated if the bundle is lost.

ug24-setup.sh
#!/bin/sh
# Install the uG24 runtime, simulator and test scripts after the LLVM build.
#
# Run this from the top of the working directory (the one containing
# llvm-project/ and build-ug24/) once `ninja` has produced build-ug24/bin/clang.
#
#   ./ug24-setup.sh [build-dir]      default build dir: build-ug24
#
set -e

ROOT=$(cd "$(dirname "$0")" && pwd)
BUILD=${1:-build-ug24}

[ -x "$ROOT/$BUILD/bin/clang" ] || {
    echo "error: $ROOT/$BUILD/bin/clang not found." >&2
    echo "Build the uG24 toolchain first - see the handbook, section 6." >&2
    exit 1
}

echo "==> building the uG24 runtime (crt0, libug24, linker script, headers)"
"$ROOT/ug24-runtime/build-runtime.sh" "$BUILD"

echo "==> building the simulator"

Why the runtime is built with -ffreestanding -fno-builtin

Without those flags the optimiser recognises the shift and memcpy loops inside the helpers and rewrites them as calls to the very functions being defined — producing infinite recursion at run time. build-runtime.sh passes both.

9

Wrapper scripts and CMake toolchain files

Wrappers encode the triple, sysroot and GCC installation so the toolchain is a drop-in replacement for the GNU cross compiler.

9.1 Shell wrappers

The heredoc delimiter must be quoted

Use << 'WRAPPER' with quotes. Without them the shell expands $(dirname "$0") and "$@" while writing the file, producing a wrapper that execs /clang and drops all arguments. That is exactly what happened in the previous build.

shell — armhf
TBIN=$LLVM_WORK/toolchain-armhf/bin

cat > $TBIN/arm-linux-gnueabihf-clang << 'WRAPPER'
#!/bin/sh
exec "$(dirname "$0")/clang" \
    --target=armv7-linux-gnueabihf \
    --sysroot=/usr/arm-linux-gnueabihf \
    --gcc-toolchain=/usr \
    -fuse-ld=lld "$@"
WRAPPER
chmod +x $TBIN/arm-linux-gnueabihf-clang

cat > $TBIN/arm-linux-gnueabihf-clang++ << 'WRAPPER'
#!/bin/sh
exec "$(dirname "$0")/clang++" \
    --target=armv7-linux-gnueabihf \
    --sysroot=/usr/arm-linux-gnueabihf \
    --gcc-toolchain=/usr \
    -fuse-ld=lld "$@"
WRAPPER
chmod +x $TBIN/arm-linux-gnueabihf-clang++

Repeat for arm64, substituting toolchain-arm64, aarch64-linux-gnu and /usr/aarch64-linux-gnu.

Troubleshooting

Every entry was encountered during a real build.

cannot open crtbeginS.o · unable to find library -lgcc

A cross link draws from two places. The sysroot supplies crt1.o, crti.o, crtn.o and libc; the GCC installation supplies crtbeginS.o, crtendS.o and libgcc. Clang does not locate Debian's /usr/lib/gcc-cross layout on its own, so it emits those as bare filenames with no path.

fix
clang ... --gcc-toolchain=/usr

# confirm it took effect
clang ... -v 2>&1 | grep "Selected GCC installation"
expected 
Selected GCC installation: /usr/lib/gcc-cross/arm-linux-gnueabihf/13

qemu-arm: Could not open '/lib/ld-linux-armhf.so.3'

The link succeeded — this is a runtime failure. The binary is dynamically linked and qemu is looking for the ARM loader in the x86 root.

fix — either
clang ... -static
qemu-arm -L /usr/arm-linux-gnueabihf ./hello-arm

instruction requires: VFP2 (building compiler-rt)

compiler-rt was added to LLVM_ENABLE_RUNTIMES for the bare-metal build, so the sub-build selected -mfloat-abi=soft. Remove it from that build and follow §7.2 instead.

undefined symbol: __aeabi_ldivmod (bare metal)

The bare-metal builtins were not built or not installed where clang looks. Check with -print-libgcc-file-name (§7.2.1); if the printed path does not exist, redo §7.2.

stdio.h not found

--sysroot is unset or empty. An unset shell variable expands to --sysroot=, which clang silently ignores. Check with ls $SYSROOT_ARMHF/include/stdio.h.

The wrapper script execs /clang

The heredoc delimiter was unquoted, so $(dirname "$0") was expanded at write time. Recreate it with << 'WRAPPER' — see §9.1.

The build is killed part-way through

Out of memory during linking; confirm with dmesg | grep -i oom. Keep -DLLVM_PARALLEL_LINK_JOBS=1 and lower ninja -j.

ninja rebuilds hundreds of targets for no reason

A system library update touched a timestamp, so ninja considers llvm-min-tblgen stale and cascades a relink. Harmless, about a minute. The build is done when ninja says no work to do.

undefined symbol __mulsi3 / __adddf3 (uG24)

The program uses long, float or double. Those uG24 runtime helpers are not implemented. Use char, short or int.
