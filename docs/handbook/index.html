01

What exists

The uG24 is a custom 8-bit RISC core with a 16-bit address space, 16 general-purpose registers and 16-bit fixed-width instructions. Nothing existed for it, so every stage below was written: there is no upstream compiler, linker or emulator to fall back on.

02

How it was built

The instruction set came from the spreadsheet, not the PDF

Two source documents were supplied. uG24081616uP_spec.pdf is a hardware engineering specification — clocks, resets, bus interfaces, TCM configuration. It contains no opcode tables. Copy of uG24xx1616uP_ISA.xlsx does, and it is the authoritative source for every encoding in the backend.

The spreadsheet's uG24081616uP_ISA sheet gives, for each instruction, its mnemonic, operation, length and the bit-field layout across positions 15 down to 0. The uG24081616uP_Registers sheet gives the register file and the PSW bit assignments. Both were transcribed field by field into TableGen.

Worth knowing

An earlier draft of the backend had most opcodes wrong — NOP and WFI swapped, RET encoded as NOP, branches using the wrong two low bits, LJA's target address never encoded at all, and XORI missing entirely. Rebuilding the machine description directly from the spreadsheet fixed all of it. Every encoding is now pinned by a regression test.

Six formats carry the whole instruction set

The low bits of each halfword select the encoding class, which is what makes a compact decoder possible:

SelectorFormatInstructions
Inst{0} = 1I — immediateLD, MVI, ST, ANDI, ORI, XORI, ADI, SBI
Inst{1:0} = 10B — branch12 conditional branches, JR, LJR, JI, LJI
Inst{3:0} = 0000P — impliedSWAP, MUL, DIV, CMP, JA, LJA, machine control
Inst{3:0} = 0100S — stack/moveMOV, PUSH, POP and their SFR forms
Inst{3:2} = 10A — arithmeticADD, ADC, SUB, SBB, INC, DEC
Inst{3:2} = 11L — logic/shiftAND, OR, XOR, NOT, LSL, LSR, RSL, RSR, ASR, CLRF, INVF

Making an 8-bit ALU compile C

C requires int to be at least 16 bits, but the uG24 ALU is 8 bits wide. Three mechanisms bridge that gap:

  • Byte-pair arithmetic. Every 16-bit add, subtract or bitwise operation is selected as a pseudo instruction and split after register allocation into two byte operations, with ADC/SBB carrying between halves.
  • Constant shift expansion. A 16-bit shift by a constant becomes byte shifts plus an OR — never a function call. Only variable shift amounts reach the runtime.
  • Two-stage comparison. A 16-bit compare tests the high bytes, then the low bytes when the high bytes match. Signed comparisons flip both sign bits first and use the unsigned ordering, which is exact and avoids depending on an ambiguity in the spec.

Two registers are reserved

R11 is the expansion temporary: ADC and SBB take a register operand, so adding a 16-bit constant needs somewhere to put its high byte. R15:R14 (DPTR0) is the memory base register, because LD and ST read their base address from DPTR0 implicitly rather than from an encoded operand. Everything else is allocatable.

The instruction set only names three register pairs, because only three fit its 3-bit extended-register field. But that field is used by just four instruction forms; ordinary 16-bit arithmetic works on any adjacent pair. The compiler therefore treats all eight pairs as 16-bit registers and restricts only those four forms — without this, two usable 16-bit registers would mean near-constant spilling.

Decisions the spec forced

The source documents leave four things genuinely undetermined. Each was resolved by an explicit assumption, isolated to as few places as possible so it is cheap to change. These need confirmation from whoever owns the hardware.

AmbiguityAssumption madeChange it in
Branch displacement units. Branches are written PC ← PC + 1 + i10, but instructions are 2 bytes. The field is a signed count of instruction words from the following instruction: target = branch + 2 + i10×2. This is the only reading consistent with LJA's RA ← PC + 2. UG24AsmBackend.cpp
lld Arch/UG24.cpp
ug24sim.c
CMP signedness. The sheet says PSW.LT = (Rs1 < Rs2) without saying signed or unsigned. Unsigned, with PSW.Cy also receiving the borrow. The compiler never depends on this: signed comparisons flip both sign bits first, so if the hardware turns out to compare signed, the flip is merely redundant. UG24ISelLowering.cpp
(translateCC)
Stack direction. PUSH stores then decrements; POP loads then increments. As written these are not inverses. Full-descending: decrement then store, load then increment, so a push/pop pair round-trips. Multi-byte pushes are little-endian. ug24sim.c
UG24FrameLowering.cpp
Extended register width. Written as 100_0 in some tables and 100 in others. Three bits, holding the GPR index shifted right by one. Resolved from the encoding diagrams, which leave exactly three bits for the field. UG24RegisterInfo.td

One further gap is not an ambiguity but an absence: the specification defines no C ABI. The calling convention below was invented and is documented in docs/uG24-assumptions.md.

04

Building the toolchain

The toolchain is already built in build-ug24/. These steps are for rebuilding from scratch on another machine.

Configure

shell
cd ~/llvm-arm-cross
cmake -G Ninja -S llvm-project/llvm -B build-ug24 \
  -DCMAKE_BUILD_TYPE=Release \
  -DLLVM_TARGETS_TO_BUILD="UG24;AArch64;ARM" \
  -DLLVM_ENABLE_PROJECTS="clang;lld"

Compile

shell
ninja -C build-ug24 clang lld llc llvm-mc llvm-objdump llvm-readobj llvm-nm llvm-ar

Runtime and simulator

shell
./ug24-runtime/build-runtime.sh build-ug24
cc -O2 -o ug24-sim/ug24sim ug24-sim/ug24sim.c

build-runtime.sh compiles the startup file and helper library with the compiler that was just built, then installs crt0.o, libug24.a, ug24.ld and include/ug24.h into build-ug24/lib/ug24/ — which is where the clang driver looks for them.

If ninja rebuilds unexpectedly

A system library update can touch a timestamp that makes ninja consider llvm-min-tblgen stale, cascading a relink of roughly eighty targets. This is harmless and takes about a minute. The build is complete when ninja reports no work to do.

05

Running a file

There is no operating system on this target and no standard library. Printing works through a memory-mapped UART that the simulator models, declared in ug24.h.

hello.c

c
#include <ug24.h>

int main(void) {
    ug24_println("Hello ug24");
    return 0;
}

Compile, link and run

shell
~/llvm-arm-cross/build-ug24/bin/clang --target=ug24-unknown-none-eabi -Os hello.c -o hello.elf
~/llvm-arm-cross/ug24-sim/ug24sim hello.elf --quiet

Hello ug24

That single clang invocation runs the front end, the uG24 code generator, the integrated assembler and the linker, pulling in the startup file, the runtime library and the memory layout automatically.

A fuller example

The helpers cover decimal and hexadecimal output, which is usually enough to check a computation without a debugger:

c
#include <ug24.h>

int main(void) {
    ug24_println("Hello ug24");

    ug24_puts("  8-bit multiply 12 * 11 = ");
    ug24_put_u16((unsigned char)(12 * 11));
    ug24_putchar('\n');

    ug24_puts("  16-bit sum 1..100    = ");
    unsigned short sum = 0;
    for (unsigned short i = 1; i <= 100; i++)
        sum = (unsigned short)(sum + i);
    ug24_put_u16(sum);
    ug24_putchar('\n');

    ug24_puts("  hex of 48879         = 0x");
    ug24_put_hex16(48879);
    ug24_putchar('\n');
    return 0;
}
output
Hello ug24
  8-bit multiply 12 * 11 = 132
  16-bit sum 1..100    = 5050
  hex of 48879         = 0xbeef

06

Inspecting output

Without a UART

A program that computes rather than prints can leave its results in global variables — locals disappear when a function returns — and --dump writes the whole 64 KB memory to ug24-memory.bin for inspection.

shell
~/llvm-arm-cross/ug24-tests/ug24-run.sh mytest.c results total

halted after 289 instructions
return value: r0=230  w=14
  results      @0x000000e2  00010409
  total        @0x000000e6  0e00

ug24-run.sh compiles, links, runs and then looks up each named global in the symbol table and prints its bytes. Note that multi-byte values are little-endian: 0e00 is 14, not 3584. A byte-sized return value appears in r0; a 16-bit one appears in w.

Seeing the generated code

shell
# assembly, before assembling
clang --target=ug24-unknown-none-eabi -Os -S hello.c -o -

# disassembly of the linked image
llvm-objdump -d --triple=ug24-unknown-none-eabi hello.elf

# headers, sections and relocations
llvm-readobj --file-headers --relocations hello.o

Simulator options

If it never halts

stopped after 20000000 instructions without halting means an infinite loop. Run again with --max 100000 --trace and look at the tail of the trace to find where it spins.

Calling convention

  • 8-bit arguments in R0–R3, then the stack.
  • 16-bit arguments in W, then DPTR1, then the stack.
  • Returns: a byte in R0, sixteen bits in W.
  • RA holds the return address and is clobbered by the next call, so any non-leaf function pushes and pops it.

Memory map

RangeContents
0x0000 – ….text, then .rodata, .data, .bss
… – 0xFEFEStack, growing downwards from __stack_top
0xFF00UG24_UART_TX — write a byte to print it
0xFF01UG24_UART_STATUS — bit 0 set when ready
0xFF02UG24_SIM_EXIT — write to halt with that status

The peripheral window is a simulator convention, not hardware. Change it in ug24.h, ug24.ld and ug24sim.c together to match a real SoC.

The execution suite is the important one: it compiles C, links it, runs it on the simulator and checks the computed values, so a fault anywhere in the chain shows up as a wrong answer rather than passing silently.

09

Known limits

These are deliberate scope boundaries, not defects. Each fails loudly rather than producing wrong code.

Not supportedWhat happens
float, double, long arithmeticLink error naming the missing helper, e.g. __mulsi3
Signed and 16-bit divisionWorks, but through software helpers — the hardware DIV is 8-bit unsigned only
Variable-length allocaRejected during lowering
Debug informationNo DWARF is emitted; debug with --trace
Computed goto, jump tablesExpanded into compare-and-branch chains; JI/LJI assemble but are not selected
Interrupt handlersNo attribute or vector table support yet

The largest single piece of remaining work is a 32-bit and floating-point helper library, which would remove the first row entirely. It can be written in C and compiled with this toolchain, the way ug24_builtins.c already is.
